# API・データ・課金の設計

そろうよが管理するのは、誰がどのグループに所属し、どの日に回答し、何を確定したか。本人確認はWorkOS AuthKit、契約と利用権はStripeを正本とする。[全体構成・選定理由・料金](./architecture.md)

## 操作者と権限

| 操作者 | 本人やアクセス権の確認 | できること |
| --- | --- | --- |
| 主催者 | AuthKitのセッションと、D1にある所属・対象調整の作成者ID | 自分の調整の作成・集計・確定・取り消し。グループ管理操作はそのグループの管理者に限定する。 |
| グループメンバー | AuthKitのセッションと対象グループへの所属 | 所属先の予定を重ねて見る、所属先で調整を作る、自分の回答を更新する。所属と支払者は別々に扱う。 |
| リンク回答者 | その調整に限って有効な招待トークン。送信者の再識別にはブラウザごとのゲスト用Cookieを使う。 | 招待された調整に回答し、確定後は同じリンクで決定日を確認する。グループの他の予定やメンバー一覧は公開しない。 |

主催者とメンバーはAuthKitのホスト画面でログインする。多要素認証を `Required` に設定し、パスワード入力後の認証アプリの登録とコード検証をAuthKitに任せる。ゲストの回答画面はこのログイン処理を呼び出さない。[AuthKitの多要素認証](https://workos.com/docs/authkit/mfa)

Workerがログインを開始し、`/api/auth/callback` でブラウザに紐づけた一回限りの `state` を照合してから認可コードを交換する。WorkOS SDKで暗号化したセッションを同一オリジンのCookie（Secure、HttpOnly、SameSite=Lax）に保存する。会員APIは環境ごとのClient IDに対応する公開鍵で署名を検証し、発行者・有効期限を確認する。アクセストークンの期限が切れたらSDKでセッションを更新してCookieを置き換える。ログアウト時はCookieを削除し、WorkOSのセッションも終了する。[セッション管理](https://workos.com/docs/authkit/sessions) · [WorkOS SDK](https://github.com/workos/workos-node)

Workerは検証済みの `(iss, sub)` をD1の内部ユーザーに対応させ、操作対象ごとに所属・役割・作成者を確認する。Cookieを使う更新リクエストではOriginも照合する。

グループ参加用リンクと日程調整の回答用リンクは用途・対象・失効状態を区別する。前者はログイン後に明示的に「参加」を選んで初めて所属を作る。後者はスマホのブラウザだけで完結する。リンクは共有した相手に転送できるため、ゲストの表示名は自己申告として扱う。

## D1に保存するデータ

| データ | 関係・制約 |
| --- | --- |
| 利用者・グループ・所属 | 利用者は `(issuer, subject)` が一意。グループに名前・色・作成者を持たせ、所属は `(group_id, user_id)` が一意。所属に役割を持たせる。 |
| 調整・候補日 | 調整はグループ・作成者・回答締切・選択済み候補を持つ。候補は安定したIDで識別し、並び替えても票の対応が変わらない。 |
| 回答・投票 | 回答は `(poll_id, respondent_key)` が一意。投票は `(answer_id, candidate_id)` が一意で、値は○△×の3値。未入力は票のない状態。対象調整が同じ候補だけを受理する。 |
| 予定 | グループ・日付・任意の開始時刻・タイトルを持つ。調整から作った予定は `source_poll_id` が一意、通常予定はNULL。月表示用に `(group_id, date)` の索引を置く。 |
| 招待 | 用途、対象、ランダムトークンのハッシュ、期限・失効日時を保持する。参加リンクは発行から7日で期限切れとし、失効していないものはグループごと1本まで。回答リンクは失効していないものを調整ごと50本まで。グループの削除・参加リンクの再発行では対象リンクを無効化する。 |
| 計測イベント | イベント種別・匿名訪問者ID・招待/調整の内部ID・発生日だけを保持する。表示名・予定名・コメント・リンク秘密部分は保存しない。`event_type + invite_id + visitor_id` を一意にして再送を除外する。 |
| 購入との対応（販売開始後） | 利用者とStripe Customer IDを一対一で対応付ける。購入開始の再試行に必要な試行ID・Checkout Session IDを保持する。請求履歴や購読状態の台帳はStripeで管理する。 |

初回の表示タイムゾーンは日本向けに `Asia/Tokyo` とする案。終日予定は日付のまま、締切など判定が必要な瞬間はUTCで記録する。どのグループの予定が見えるかはサーバー側のクエリで絞り込み、ブラウザに届く時点で閲覧可能なものだけにする。

## 招待から確定まで

1. **主催者が調整を作る。** `/polls/new` でカレンダー上の複数日を選び、予定名・グループ・候補ごとの開始時刻・回答締切を入力する。API（`POST /api/groups/:id/polls`）は所属を確認し、調整・候補日・回答リンクを作る。調整の一覧は `GET /api/polls` が所属グループ分を状態・件数つきで返し、`/polls` で開く。リンク例は `/r#<token>`。URLフラグメントを同一オリジンの画面が読み取り、POST本文でAPIに渡す。D1にはハッシュだけを保存する。アクセスログや計測にリンクの秘密部分・回答本文・Cookieを記録しない。
2. **ゲストが○△×を送る。** Workerはリンクの用途・失効状態・締切を確認する。回答画面を開く際に推測困難なゲスト用Cookieを確立し（Secure、HttpOnly、SameSite=Lax）、書き込み時はOriginも確認する。回答者キーは調整とゲスト識別子から導き、同じブラウザでは既存回答を更新する。名前が同じ別人の票は統合しない。Cookieを消した場合、LINEの内蔵ブラウザからSafariなど別ブラウザへ移った場合、別端末での同一人物判定には限界がある。登録メンバー本人の回答として記録する場合はその人のログインを用いる。
3. **別の端末で回答状況を見る。** 主催者が回答状況を開き直すと、D1から候補別の○△×と回答者別の内訳を取得する。2人の同時回答は別の回答行として残す。画面表示後に締切や確定を迎えることがあるため、回答の書き込みでも受付中かを判定する。
4. **主催者が1日を確定する。** 対象調整の作成者であることと、候補がその調整に属することを検査する。D1のトランザクションバッチで未確定からの条件付き更新を行い、DBで選択された候補から予定を生成する。`source_poll_id` の一意制約で二重登録を防ぐ。バッチ後、同じ候補の再送には既存結果、別候補が先に確定していれば競合を返す。条件付き更新が0行でもバッチは失敗しないので、クライアントが要求した候補をそのまま挿入しない。[D1のbatch](https://developers.cloudflare.com/d1/worker-api/d1-database/)
5. **結果を共有する。** メンバーは月カレンダーで、ゲストは回答リンクで確定日を確認する。取り消しも調整の状態変更と `source_poll_id` に対応する予定の削除を同じバッチで行う。候補と既存の票を保持するが、受付再開には必ず新しい締切の設定が必要になる。

受付中の調整は作成者だけが編集でき、タイトル・締切・候補を変更できる。候補の日時変更は削除と追加として扱い、その候補の票だけを消す。編集画面の表示後に回答や別の変更が入った場合は `edit_version` の楽観的排他で409を返し、開いていた画面から新しい票を見落としたまま上書きしない。確定済みの調整は編集・削除できず、先に確定取消を行う。通常予定はグループメンバーが編集・削除でき、調整から作られた予定はタイトルとメモだけを直接編集する。

グループ作成は1人5件まで。`POST /api/groups` は作成者の件数判定とグループ行の挿入を1つのSQLで行い、超過時は409を返す。招待で参加したグループは作成数に含めず、作成したグループを削除するとその分だけまた作れる。画面は上限に達したことと、上限を超えている場合は作成済みが上限未満になるまで不要なグループを削除すれば再作成できることを、入力内容を残したまま表示する。移行期間に `created_by` がない行は、最初のadminを作成者とみなして数える。

調整はグループごと50件まで、通常予定はグループごと300件まで、回答リンクは調整ごと50本まで。候補日は1回の調整で31件までの既存制限に加え、これらの累積上限でD1の保存量を抑える。作成APIは件数判定と挿入を1つのSQLで行い、超過時は409を返す。通常予定の上限には調整確定で自動生成される予定を含めず、削除するとその分だけまた作れる。

グループへの参加リンクは `/join#<token>`。発行から7日で期限切れとし、有効なリンクはグループごと1本だけにする。管理者がグループ詳細から再発行すると旧リンクを同じバッチで失効させ、無効化すると共有済みリンクからは参加できなくする。受け取った人はプレビューでグループ名・招待した人・参加すると見える内容を確認し、ログイン後に明示的な「参加」操作でのみメンバーに加わる。開き直しても二重に加えず、既にある役割（管理者など）は保つ。ログインが必要な画面からの遷移は `?next=` で戻り先を保持し、認証後に元のリンクへ戻す。

メンバーの除名と脱退は `DELETE /api/groups/:id/members/:userId` が扱う。グループ作成者だけが他のメンバーを除名でき、メンバーは自分の所属だけを削除して脱退できる。作成者は自分を除名・脱退できず、グループを畳む場合はグループ削除を使う。除名では所属の削除と現在の参加リンクの失効を同じバッチで行い、脱退では参加リンクを変えない。外れた人は以後そのグループの予定・日程調整を閲覧・操作できないが、以前に入れた予定・日程調整・回答と名前表示は残す。

回答の受付条件はDBへの書き込みにも含める。回答行の作成・更新と各票の作成・削除・更新は、いずれも対象調整が受付中であることをSQLの条件に含め、同一バッチで実行する。受付中でなければ条件付きの書き込みは0行で終わるので、APIは影響した行数を確認して受付終了を返す。外部キー違反はエラーになり、バッチ全体をロールバックする。確定と回答が重なったときは、確定より先に成立した回答だけが残る。失効したリンクには対象情報を出さず、締切後・確定後の有効なリンクにはその調整の状態を返す。

ログイン不要の回答APIは、招待トークンと回答者識別子（ゲストはゲスト識別子、メンバーは利用者ID）の組み合わせごとに短時間の更新回数を制限する。既定は1分10回で、Workers Rate Limiting bindingで送信元IPごとに1分60回も制限する。Workers Rate LimitingのカウンターはCloudflareの拠点ごとに管理され、サービス全体への厳密な総量上限ではない。上限は `wrangler.jsonc` のbinding設定で変更し、bindingがないテスト環境では同じ既定値のフォールバックを使う。制限に達した場合は429を返し、既存回答を変更しない。[Workers Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)

## 招待到達率の計測

- **有効リンク訪問（分母）**: `POST /api/invite` で用途・失効・対象調整が有効と確認できた回答リンクの表示。無効リンクやAPIエラーは含めない。締切後・確定後でも、有効リンクを開いた訪問は分母に含める。
- **回答完了（分子）**: 同じ有効リンクからの `POST /api/invite/answer` が受付中の調整に書き込み受理された回答。締切後・確定後・権限エラーは含めない。
- **同一性と再送**: 匿名のゲストCookieを訪問者IDとし、`イベント種別＋招待の内部ID＋訪問者ID` を一意にする。同じブラウザでの再読込・回答更新・API再送は1件に数え、再発行された別リンクは別の招待として数える。Cookie消失や別ブラウザ移行は別訪問者になる限界がある。
- **利用開始**: 回答完了画面の「自分のグループを作る」クリックを `usage_start_click`、ゲスト回答者がログインして最初の自分のグループを作った時点を `usage_start` として、同じ匿名訪問者IDで記録する。クリックは `/groups?create=1` へ進み、ログイン後もこの指定を引き継いで作成フォームを開く。回答元グループへの所属や管理権限は作らない。利用開始済みの匿名訪問者は、別の招待に回答してから作り直しても再計上しない。
- **集計期間**: 内部API `GET /api/analytics/funnel` は既定で直近30日をAsia/Tokyoの日別に返す。`days` は1〜90。日別・期間合計とも `回答完了 / 有効リンク訪問`、`usage_start_click / 回答完了`、`usage_start / 回答完了` を返し、分母0の率はNULL。運用者だけがWorkerのSecret `ANALYTICS_TOKEN` をBearerトークンに使って読む。
- **将来の率**: 作成者から有料契約に進んだ割合は `checkout_completed` を同じ匿名イベント構造に追加して区別する。購入機能（#17）の提供後に発火箇所を足し、表示名・予定名・コメント・リンク秘密部分は今後のイベントにも含めない。

## データの削除

| 要求 | そろうよの処理 | 外部サービス |
| --- | --- | --- |
| 会員の退会 | D1の所属を解除し、利用者と認証の対応・表示名を削除する。本人が作成した調整や予定は、グループの利用に必要なものを削除済み利用者の記録として残し、不要な個人情報は保持しない。 | ログアウト後にWorkOSの利用者を削除する。Stripeの請求・契約記録は外部の正本として扱い、D1のCustomer対応だけを解除する。保存期間と削除範囲は法務の結論に合わせる。 |
| グループの削除 | 対象グループの所属、予定、調整、候補、回答、招待をD1のバッチで削除する。 | 各メンバーのWorkOS利用者やStripe契約は消さない。 |
| ゲストの回答削除 | 対象調整のリンクとゲスト識別子で本人性を確認し、回答・票・ゲスト表示名を削除する。招待トークンのハッシュは失効または調整削除まで残す。 | ゲストにWorkOSアカウントやStripe Customerは作らないため、外部削除は不要。 |

## 課金を外部に任せる境界

販売開始時に、価格と請求周期をStripeのPriceに、有料機能をProductに紐づくEntitlementsに設定する。支払者を作成者とする案、無料グループ数、候補日上限などは [#30](https://github.com/Riku10145/sorouyo/issues/30) の結論に合わせる。アプリが守るのは「この操作を誰に許すか」で、請求・更新・支払再試行・契約解約・契約期間の計算はStripeが扱う。

| 場面 | そろうよの処理 | Stripeの処理 |
| --- | --- | --- |
| 購入開始 | 認証済み本人のCustomerと、サーバーで許可したPriceを使いCheckout Sessionを作成する。未完了の購入試行は再利用し、同じ試行のAPI再送には同じ冪等キーを使う。既契約者は契約管理へ案内する。 | ホスト型Checkoutで支払情報を受け取り、契約・決済を処理する。 |
| 購入後・有料操作 | 成功画面へのリダイレクトでは利用権を付与しない。本人または対象グループの支払者に対応するCustomerのActive EntitlementsをStripe APIで照会し、対象機能のキーが有効な場合に操作を許可する。無料枠の件数判定はD1で書き込みと一体にする。 | 契約状態に応じて利用権を更新し、対象Customerに有効な機能を返す。 |
| 契約変更・解約 | 本人のCustomerで短命なPortal Sessionを発行して遷移する。復帰時に契約による利用権を再照会する。 | Customer Portalで支払手段・請求書・設定で許可した解約や変更を扱う。 |

初回は有料操作時の照会を選ぶので、Webhook購読・イベント再送処理・利用権の定期同期を運用せずに済む。Stripeの応答が遅れた購入直後は反映待ちと再確認を表示し、障害時は新規購入と有料操作のみ再試行を案内する。既存予定の閲覧とゲストの回答は継続する。照会の頻度や遅延が問題になった段階で、署名検証付きWebhookと再照合を備えたローカルキャッシュを検討する。[Checkout](https://docs.stripe.com/payments/checkout/build-subscriptions) · [Customer Portal](https://docs.stripe.com/customer-management) · [有効な利用権の照会](https://docs.stripe.com/api/entitlements/active-entitlement/list) · [冪等リクエスト](https://docs.stripe.com/api/idempotent_requests)

## 配布と確認

- Wranglerで検証・本番のWorkerとD1バインディングを分ける。WorkOSの環境ごとにコールバック先・ログアウト先とMFA必須設定を登録し、APIキー・Cookie暗号化鍵をWorkerのSecretに格納する。公開前に、認証コード未入力では会員APIを使えず、正しいコードの入力後に自分のグループを開けることを確認する。Stripeもテスト環境と本番を分離し、秘密鍵をWorkerのSecretとして注入する。
- D1変更は検証DBで既存データに適用してから本番へ進める。追加・移行を先に行い、旧Workerでも読める期間を設けてから不要な列を整理する。Workerの切り戻しとデータの復元は別操作として扱う。D1 Time Travelの復元可能期間はFreeで7日、Paidで30日。[D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)
- リリース前は主催者の端末と別ブラウザのゲストで回答→集計→確定を通す。同じ回答の再送、同時確定、所属外データへのアクセス拒否、締切をまたいだ送信もAPIテストに含める。販売時はStripeテスト環境で購入成功・中断・解約後の利用権・照会失敗時も確認する。[公開前の確認 #31](https://github.com/Riku10145/sorouyo/issues/31)
