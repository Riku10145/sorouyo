# 予定通知の採用判断（#32）

予定を忘れたくない人向けに、所属グループの予定を通知する。初回の採用判断をここに記録する。

## 決めたこと

| 観点 | 判断 | 理由 |
| --- | --- | --- |
| 通知手段 | **ブラウザの通知APIによるローカル通知**（最小のService Worker `public/sw.js` 経由。AndroidのChromeは `new Notification()` を受け付けず `ServiceWorkerRegistration.showNotification` が必要なため）。アプリを開いている間は指定時刻にタイマーで届き、開いた時点で当日分が未通知ならその場で1回届く。 | Web PushはVAPID鍵の管理・購読の保存・定期実行（Workers Cron）とPWA化が前提になり、初回の配布形態（[distribution.md](./distribution.md) はWebのみ・通知なし）から要件が大きく変わる。まず利用者の設定UIと時刻の扱いを確定し、端末に届く価値を小さく検証する。 |
| 対象の予定 | **当日の全所属グループの予定**を1件の通知にまとめる。 | 予定ごとに件数分の通知を飛ばすと朝に連続して届きうる。まとめ通知なら「1回だけ」が自然に守れる。 |
| 時刻の扱い | 利用者が設定した時刻（既定8:00）の**端末ローカル時刻**。対象は通知を出す端末そのものなので、サーバー時刻やJST固定にはしない。 | 利用者は自分の端末の時計で生活している。時刻は `HH:MM` でサーバーに保存し、別端末でも同じ設定を使える。 |
| 非対応端末 | 通知APIのないブラウザでは、設定画面に「この端末・ブラウザは通知に対応していません」と表示し、トグルを出さない。カレンダーはそのまま使える。 | 通知の許可を断った場合も同様にカレンダー利用を妨げない（受け入れ条件）。 |

## 届かない条件（受け入れ条件との対応）

- 通知を切った場合: 発射のたびにサーバーの設定を読み直すので、切ったあとの発射は届かない。
- 予定を削除した場合: 発射時にカレンダーを取り直し、対象の予定がなければ通知しない。
- 同じ日に2回: 端末に最後に通知した日を記録し、当日2回目は出さない。

## 将来の検討（Web Push化）

利用者がアプリを開かなくても届けるには、PWA化とWeb Push（VAPID・購読の保存・Workers Cronでの送信）が必要。設定データ（有効か・時刻）はサーバーにあるため、移行時に設定を引き継げる。PWA化の判断は [distribution.md](./distribution.md) の方針どおり、継続利用者の需要を見て行う。
