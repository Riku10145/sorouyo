# explain-pr

引数で渡された GitHub PR を、プログラミング初学者にもわかるように簡潔に解説する。

## 手順

1. **引数から PR を特定する**
   - URL（`https://github.com/owner/repo/pull/N`）なら owner / repo / N を取り出す。
   - 番号だけなら、現在のリポジトリ（`git remote -v`）の owner / repo を使う。
   - 特定できなければ、ユーザーに聞く。

2. **PR の情報を取得する**（独立した呼び出しなので並列で実行）
   - `mcp__github__pull_request_read` の `method: get`（タイトル・説明・状態）
   - `mcp__github__pull_request_read` の `method: get_files`（変更ファイルと差分）
   - 必要なら `get_comments` / `get_reviews` も確認する。
   - `gh` CLI や直接の API は使わない。

3. **内容を理解する**
   - 差分を読み、「何が問題で、どう直したか」を把握する。
   - PR 本文の主張は鵜呑みにせず、差分と一致しているか確認する。
   - 他の PR との関係や注意事項があれば拾う。

4. **次の構成で解説する**（日本語・簡潔に）

   ```
   # PR #N の解説

   ## ひとことで言うと
   （1〜2文。何のためのPRか）

   ## なぜ必要だったのか
   （背景・問題。専門用語は括弧で短く補足）

   ## 何を変えたか
   （表または箇条書き。ファイル単位で要点のみ。効果的なら diff を数行引用）

   ## ポイント
   （見た目や動作が変わるか、テスト・検証の状況、学べるコツ）

   ## マージ時の注意
   （他PRとの競合・依存・破壊的変更など。なければこの節は省略）
   ```

## 書き方のルール

- 初学者向け：専門用語は初出時に一言で言い換える。比喩は使いすぎない。
- 簡潔に：全体で画面1〜2枚に収める。差分の全文は貼らない。
- 事実のみ：差分から読み取れないことは推測と明記する。
- 読み取り専用：PR へのコメント投稿・レビュー・マージはしない（頼まれた場合のみ）。
